# REL006: Evitar captura de dependências scoped em hosted services

| Campo | Valor |
| ----- | ----- |
| Pacote | `CSF.Analyzers.Reliability` |
| Categoria | Reliability |
| Severidade | Warning |
| Estado padrão | Habilitada |

## Objetivo

Evitar que `BackgroundService` e implementações de `IHostedService` capturem diretamente dependências scoped conhecidas.

## Motivação

Hosted services são singletons por padrão. Capturar um `DbContext`, `IOptionsSnapshot<T>` ou outro serviço scoped configurado no construtor faz a instância scoped sobreviver pelo tempo do hosted service, causando falhas de lifetime, estado compartilhado indevido ou comportamento inconsistente.

Para dependências scoped, o padrão recomendado é criar um escopo durante a execução do trabalho e resolver a dependência dentro desse escopo. Para options em singletons, prefira `IOptionsMonitor<T>`.

## Código não conforme

```csharp
public sealed class Worker : BackgroundService
{
    private readonly AppDbContext _db;

    public Worker(AppDbContext db)
    {
        _db = db;
    }
}
```

```csharp
public sealed class Worker(IOptionsSnapshot<WorkerOptions> options) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _ = options.Value;
        return Task.CompletedTask;
    }
}
```

## Código conforme

```csharp
public sealed class Worker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public Worker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    }
}
```

```csharp
public sealed class Worker(
    IDbContextFactory<AppDbContext> factory,
    IOptionsMonitor<WorkerOptions> options) : BackgroundService
{
}
```

## Heurística

A regra analisa classes que herdam direta ou indiretamente de `Microsoft.Extensions.Hosting.BackgroundService` ou implementam direta ou indiretamente `Microsoft.Extensions.Hosting.IHostedService`.

Ela reporta:

- parâmetros de construtor clássico cujo tipo scoped conhecido/configurado é atribuído diretamente a field ou propriedade de instância;
- parâmetros de primary constructor scoped conhecidos/configurados usados em membros de instância;
- fields de instância scoped conhecidos/configurados quando não há captura de construtor correspondente no mesmo tipo.

Tipos conhecidos como scoped:

- `Microsoft.EntityFrameworkCore.DbContext` e tipos derivados;
- `Microsoft.Extensions.Options.IOptionsSnapshot<T>`.

Tipos conhecidos como seguros por padrao:

- `Microsoft.Extensions.DependencyInjection.IServiceScopeFactory`;
- `Microsoft.EntityFrameworkCore.IDbContextFactory<TContext>`;
- `Microsoft.Extensions.Options.IOptionsMonitor<T>`;
- `Microsoft.Extensions.Options.IOptions<T>`;
- `System.IServiceProvider`.

`IServiceProvider` nao e reportado apenas por existir. Service Locator e uma preocupacao diferente e nao faz parte desta regra.

## Opções públicas

Configure tipos customizados scoped com uma lista separada por `;`:

```ini
[*.cs]
dotnet_diagnostic.REL006.scoped_type_patterns = MyApp.Data.*;MyApp.Scoped.*
```

Os padrões usam o nome totalmente qualificado do tipo. `*` casa zero ou mais caracteres. A comparação é ordinal e case-sensitive.

Entradas vazias e duplicadas são ignoradas. Entradas inválidas também são ignoradas individualmente. A primeira versão aceita até 64 padrões válidos, com até 256 caracteres por padrão, e não emite diagnóstico para configuração inválida. Tipos conhecidos continuam ativos mesmo quando a configuração customizada está ausente ou inválida.

## Fallback de configuração

Sem `dotnet_diagnostic.REL006.scoped_type_patterns`, apenas `DbContext`/derivados e `IOptionsSnapshot<T>` são tratados como scoped conhecidos.

Use `dotnet_diagnostic.REL006.severity` para ajustar a severidade.

## Limitacoes

A regra não conhece o lifetime de todos os serviços do container. Ela não infere chamadas `AddScoped`, `TryAddScoped`, factories, delegates ou extensões customizadas de DI. Tipos scoped customizados precisam ser configurados explicitamente.

A regra também não valida se o hosted service foi registrado corretamente no container e não segue resoluções feitas por service locator. Dependências resolvidas depois da criação de um escopo dentro do método de execução não são reportadas.

## Impacto esperado

Reduz bugs de lifetime em workers e hosted services, especialmente captura acidental de `DbContext` ou `IOptionsSnapshot<T>` em componentes singleton.

## Suppression

Suprima apenas quando a dependencia capturada for segura por contrato externo ou quando a classe nao for registrada/executada como hosted service apesar de implementar a interface.

## Relacao com ferramentas externas

Validações de DI em runtime podem detectar algumas inconsistências de lifetime. `REL006` complementa essas validações ao sinalizar, em código-fonte, capturas conhecidas e configuradas em hosted services.
