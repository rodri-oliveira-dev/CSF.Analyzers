# REL006: Evitar captura de dependencias scoped em hosted services

| Campo | Valor |
| ----- | ----- |
| Pacote | `Swa.Analyzers.Reliability` |
| Categoria | Reliability |
| Severidade | Warning |
| Estado padrao | Habilitada |

## Objetivo

Evitar que `BackgroundService` e implementacoes de `IHostedService` capturem diretamente dependencias scoped conhecidas.

## Motivacao

Hosted services sao singletons por padrao. Capturar um `DbContext`, `IOptionsSnapshot<T>` ou outro servico scoped configurado no construtor faz a instancia scoped sobreviver pelo tempo do hosted service, causando falhas de lifetime, estado compartilhado indevido ou comportamento inconsistente.

Para dependencias scoped, o padrao recomendado e criar um escopo durante a execucao do trabalho e resolver a dependencia dentro desse escopo. Para options em singletons, prefira `IOptionsMonitor<T>`.

## Codigo nao conforme

```csharp
public sealed class Worker : BackgroundService
{
    private readonly AppDbContext _db;

    public Worker(AppDbContext db)
    {
        _db = db;
    }
}
```

```csharp
public sealed class Worker(IOptionsSnapshot<WorkerOptions> options) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _ = options.Value;
        return Task.CompletedTask;
    }
}
```

## Codigo conforme

```csharp
public sealed class Worker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;

    public Worker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    }
}
```

```csharp
public sealed class Worker(
    IDbContextFactory<AppDbContext> factory,
    IOptionsMonitor<WorkerOptions> options) : BackgroundService
{
}
```

## Heuristica

A regra analisa classes que herdam direta ou indiretamente de `Microsoft.Extensions.Hosting.BackgroundService` ou implementam direta ou indiretamente `Microsoft.Extensions.Hosting.IHostedService`.

Ela reporta:

- parametros de construtor classico cujo tipo scoped conhecido/configurado e atribuido diretamente a field ou propriedade de instancia;
- parametros de primary constructor scoped conhecidos/configurados usados em membros de instancia;
- fields de instancia scoped conhecidos/configurados quando nao ha captura de construtor correspondente no mesmo tipo.

Tipos conhecidos como scoped:

- `Microsoft.EntityFrameworkCore.DbContext` e tipos derivados;
- `Microsoft.Extensions.Options.IOptionsSnapshot<T>`.

Tipos conhecidos como seguros por padrao:

- `Microsoft.Extensions.DependencyInjection.IServiceScopeFactory`;
- `Microsoft.EntityFrameworkCore.IDbContextFactory<TContext>`;
- `Microsoft.Extensions.Options.IOptionsMonitor<T>`;
- `Microsoft.Extensions.Options.IOptions<T>`;
- `System.IServiceProvider`.

`IServiceProvider` nao e reportado apenas por existir. Service Locator e uma preocupacao diferente e nao faz parte desta regra.

## Opcoes publicas

Configure tipos customizados scoped com uma lista separada por `;`:

```ini
[*.cs]
dotnet_diagnostic.REL006.scoped_type_patterns = MyApp.Data.*;MyApp.Scoped.*
```

Os padroes usam o nome totalmente qualificado do tipo. `*` casa zero ou mais caracteres. A comparacao e ordinal e case-sensitive.

Entradas vazias e duplicadas sao ignoradas. Entradas invalidas tambem sao ignoradas individualmente. A primeira versao aceita ate 64 padroes validos, com ate 256 caracteres por padrao, e nao emite diagnostico para configuracao invalida. Tipos conhecidos continuam ativos mesmo quando a configuracao customizada esta ausente ou invalida.

## Fallback de configuracao

Sem `dotnet_diagnostic.REL006.scoped_type_patterns`, apenas `DbContext`/derivados e `IOptionsSnapshot<T>` sao tratados como scoped conhecidos.

Use `dotnet_diagnostic.REL006.severity` para ajustar a severidade.

## Limitacoes

A regra nao conhece o lifetime de todos os servicos do container. Ela nao infere chamadas `AddScoped`, `TryAddScoped`, factories, delegates ou extensoes customizadas de DI. Tipos scoped customizados precisam ser configurados explicitamente.

A regra tambem nao valida se o hosted service foi registrado corretamente no container e nao segue resolucoes feitas por service locator. Dependencias resolvidas depois da criacao de um escopo dentro do metodo de execucao nao sao reportadas.

## Impacto esperado

Reduz bugs de lifetime em workers e hosted services, especialmente captura acidental de `DbContext` ou `IOptionsSnapshot<T>` em componentes singleton.

## Suppression

Suprima apenas quando a dependencia capturada for segura por contrato externo ou quando a classe nao for registrada/executada como hosted service apesar de implementar a interface.

## Relacao com ferramentas externas

Validacoes de DI em runtime podem detectar algumas inconsistencias de lifetime. `REL006` complementa essas validacoes ao sinalizar, em codigo-fonte, capturas conhecidas e configuradas em hosted services.
